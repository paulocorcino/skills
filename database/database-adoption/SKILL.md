---
name: database-adoption
description: Adopt a brownfield database into `db-schema/`. Use when the user wants to import an existing database or reverse-engineer a legacy schema — alone or with the applications that use it — and bring it under governance.
---

Bring an existing database under `db-schema/` governance. The live schema is the source of facts; the repo is where it becomes governable. **The application** is any codebase the user points at — this repo, another path, or several — each one a second fact source and a known consumer of the database. With none, the adoption runs on the database alone, and step 6 reduces to its two closing questions. Standing rules:

- **Read-only.** Work read-only against the legacy database, with the credential the user provides. The extractor's `probe` subcommand reads the account's effective permissions; on a write-capable account it pauses — the driver's read-only intent is no guarantee, so the pause is real information. Put the headline permissions to the user; only their acceptance unlocks the run: re-run the probe with `--accept-write-risk` filled with a factual reason (recorded in `probe.json` and the ledger) and advance. Once given, the acceptance stands for the whole adoption, on the same login.
- **Ledger.** `.scratch/adoption/ledger.md` (local, gitignored) holds only what no script can derive: the connection recipe (the credential's source, never the credential), source dialect, chosen schemas, the location of every application, and accepted risks.
- **Baseline.** `db-schema/baseline/` is versioned governed state that travels in the same commits as the carved DDL: `inventory.<schema>.json` per adopted schema (the drift reference `inventory` writes) and `exceptions.json` — objects `excluded` or `blocked`, each with its reason (`[{"name": …, "status": "excluded"|"blocked", "reason": …}]`, optional `type` / `schema`), consumed and validated by reconcile: an entry without a reason is itself a failing finding. A missing baseline is restored from the repo, never rebuilt by re-running `inventory`, which would absorb whatever drift exists. Per-object progress is computed, not hand-tracked: `extract_<dialect>.py reconcile` derives the frontier (uncarved objects, drifted fingerprints, stale files, drops, blocked objects) from the live catalog, the baseline, and the carved files — **evidence, not self-report**. Every fresh session reads the ledger, runs reconcile, and resumes from what it reports.
- **Sampling.** Live-data queries return aggregates: counts expose scale, not values. When a question survives the catalog evidence, a 3-row sample (the dialect's row-limiting clause — `TOP (3)`, `LIMIT 3`, …) may inspect **shape**; record what the shape told you and keep the sampled values out of every file and message — they may be personal or business-sensitive. `DISTINCT` returns values: run it only on columns first classified as non-sensitive from catalog evidence (name, type, comment, cardinality), and ask the user when in doubt.
- **Delegation.** Where the agent can dispatch subagents and choose their model, mechanical work — running a script and summarizing its report, carving a batch, locating where a table or column is touched — goes to the smallest capable model, returning conclusions, not dumps. Judgment stays in the main session: interpreting a finding, classifying sensitivity, anything put to the user. A batch follows dependency order, fits one subagent's context, and needs no other batch's output; its coverage is proved by evidence, not self-report, and every *untouched* or *writer unknown* flag is re-confirmed by the main session before it is recorded — those flags drive drop decisions. Where delegation is unavailable, or the inventory is small enough that dispatch costs more than it saves, the work runs inline.

## 1. Locate the connection

Search the project and every application for how it already reaches the database: env files, `docker-compose`/Dockerfile, framework config (Django settings, Spring `application.yml`, Prisma, knexfile, …), docs. **Secret values stay out of context:** read secret-bearing files (`.env` and kin) for filenames, variable names, and structure only — the connection script reads the values from the environment at runtime. Done when you hold a connection recipe — engine, host, port, database, credential source — or have established that none exists, and every application the user named has its location in the ledger.

## 2. Wire the env

If none exists, create the project's native env convention (`.env` plus a committed `.env.example`, the real file gitignored) with placeholder variables, matching the project's language and stack. Tell the user exactly which variables to fill; credentials live in the env file only, typed there by the user, outside the chat. The env user needs read permission on the catalog and the target schemas — on a permissions failure, name the exact missing grant. Done when the user confirms the env is filled.

## 3. Probe

Run the extractor's `probe` subcommand under the read-only rule (step 4 says where the tool comes from — run it from the skill's `scripts/` reference when the repo holds no copy yet). On connection failure, show the error and fix the recipe with the user, one variable at a time. On success, `probe.json` holds the engine and version — the **source dialect**, not automatically the canonical one — and the non-system schemas. If `db-schema/.sqlfluff` is missing, propose the source dialect as canonical and ask the user to confirm or name a different target (steps in `db-schema/README.md`); if it exists and differs from the source, surface the difference and leave the file as it stands. Then put the first decision to the user: **which schemas to adopt** (the extractor works one `--schema` per pass). Done when the probe passed (or the acceptance is recorded) and the ledger holds recipe, source dialect, chosen schemas, application locations, and accepted risks — nothing more: step 4's `inventory` subcommand writes the baseline mechanically, one file per schema.

## 4. Extract and carve

Introspection is mechanical — script it. The tool is `db-schema/tools/extract_<source-dialect>.py`, a **living tool** this skill ships as versioned references in its `scripts/` folder. **The references are read-only during an adoption:** the run evolves the repo copy alone, and a reference changes only in maintenance outside any adoption run. Before extracting, sync versions name-to-name — compare `__version__` in the repo copy against the skill's reference:

- no repo copy yet → copy the matching reference into `db-schema/tools/`; when no reference covers this engine, the port is yours to build — by trial and error against the live database, before any extraction: read [`PORTING.md`](PORTING.md)
- repo copy **newer** → keep using the repo copy
- skill reference **newer** → upgrade the repo copy, reading the changelog for what changed
- equal → compare content too (a byte diff is enough): identical → proceed; different → someone changed the repo copy without bumping — diff it, bump the repo copy's version, and proceed with it

Adjust the repo copy whenever this engine or this database demands something it doesn't cover yet — and bump its `__version__` + changelog with every behavior change, or the next sync goes blind. Whenever the repo copy ends the adoption ahead of the reference — evolved, ported, or found newer — record it in the ledger and in the hand-off as a **harvest candidate**: the version, the changelog entries, and why; a maintainer carries it into `scripts/` outside the run. Carve under the delegation rule:

- tables → `db-schema/schema/tables/<table>.sql`, comments preserved — every carved file is named by the object's qualified name, `<schema>.<name>.sql` outside the default schema, so adopted schemas never share a file
- functions, procedures, triggers, views → `db-schema/schema/native/<dialect>/<kind>/` — one subfolder per kind (`functions/`, `procedures/`, `triggers/`, `views/`), per that folder's README
- support objects the engine has — sequences, synonyms, user-defined types, and kin — → `db-schema/schema/native/<dialect>/<kind>/` too. The inventory sweeps **every object class the engine supports**: defaults and routines depend on these objects, and a schema carved without them cannot be recreated
- what doesn't transpile cleanly → `db-schema/schema/overrides/<dialect>/`

Done when the inventory **reconciles**: `extract_<dialect>.py reconcile` reports every source object carved (or covered by an `exceptions.json` entry with its reason), every carved file still matching the live rendering, and no fingerprint drifted since extraction — `python db-schema/tools/verify.py` is green, and `db-schema/baseline/` sits beside the carved DDL, ready to go into the same commit. A green `verify.py` alone proves the files are well-formed, not that extraction is complete; the reconciliation proves coverage. Every object the tool reports as `BLOCKED` (encrypted modules, unsupported object classes or index types, names colliding on a case-insensitive filesystem) is a decision put to the user and recorded in `db-schema/baseline/exceptions.json` with its reason.

## 5. Populate the model

Run `python db-schema/tools/erdgen.py`, then `extract_<dialect>.py discover` — **DB-to-Domain discovery**: it ranks every table by structural relevance (who references it — tables via FK, modules via dependencies; row count only breaks ties), classifies structural roles (junction, lookup, log, core, elimination candidate, unreferenced), and clusters the FK graph — declared *plus* name-implied edges — into candidate domain areas, peeling cross-domain hub entities first. Everything it emits is a **candidate, never a fact**: clusters suggest domain areas but naming them is a human decision for the grill; `unreferenced` tables and hub entities are gaps to record; its `elimination candidate` list mechanizes the materiality rule below. Use the ranking to order the model draft and the grill — human attention goes to core candidates first, before a line of the model is written.

Then draft `docs/db-model/database.md` (skeleton and growth contract in `docs/db-model/README.md`) in discover's relevance order, from evidence only: table/column comments, constraints, and column semantics become concepts and invariants. Record what evidence cannot tell you — intent, business rules, vocabulary — as explicit gaps, and fill "Conscious divergences from the original dump" for anything deliberately changed while carving. Per-table blocks follow the materiality rule in `docs/db-model/README.md`: an empty table no routine touches and nothing references gets a one-line entry marked **elimination candidate** (an owner decision to confirm or drop); *pending* blocks are reserved for material tables.

Then run the **reality census** — read-only aggregates, scripted like the extraction: row count per table, orphan count for every implied FK, violation count for every candidate invariant. A table with **no declared primary key** is itself a census finding — the tool names one candidate key (unique index, id-ish name, or first column) and counts its duplicates and nulls; identity is the first invariant of any table, and until the grill confirms one, the per-table block carries that gap explicitly. Attach each number to its gap ("candidate invariant: violated by N rows") — the numbers size the cleanup the refactoring tickets will carry. Read the carved DDL for **type smells** — money or quantities in binary floating point, date-times without a zone, numbers or dates stored as text — each recorded as a gap; the types alone reveal them, no query needed.

In the routines table, mark every non-trivial routine **behavior not characterized** — each mark becomes a characterization ticket (approval testing: run the routine over representative inputs and freeze its outputs as the golden master) before that routine may be refactored. A routine that computes money, tax, or a figure in an official report also carries **protected candidate**; whether it becomes a protected rule is the user's decision in the grill.

Done when every adopted table has its per-table block or one-line entry, every census number is attached to a gap, every type smell is recorded, and every non-trivial routine carries its **behavior not characterized** mark — and **protected candidate** where it computes money, tax, or a reported figure.

## 6. Excavate the applications

Excavate each application for what the catalog cannot see, through two anchors — each enumerable, so coverage is checkable:

- **The table anchor** — every adopted table traced into the code, by name or through the ORM's naming convention. Around each touch, record ORM associations and joins that imply relations with **no FK behind them**, enums, state machines, and validations living only in the app layer. A table no code touches is itself a finding: evidence for its elimination candidacy, or a hint of an external consumer.
- **The value anchor** — every derived or money-like column traced back to the code that computes what is written into it, following the data from the write to the arithmetic however many calls away. Quote the mapping itself into the finding — the model's Derivation section wants it written out. A column whose writer stays unfound is recorded as **writer unknown**.

Then sweep each application for the signals the grill's later themes consume, each hit recorded as a candidate:

- **computation** — rounding calls, arithmetic on money columns, percentage-like constants, date arithmetic on deadlines, the glossary's own vocabulary (tax, fee, commission); each hit traced to the value it produces, and a money, tax, or reported figure marked **protected candidate**
- **rule parameters** — small tables read by routines or code and rarely written (rates, thresholds, price lists): **rule parameter candidate**
- **home-made queues** — triggers copying rows into `*_queue` / `*_log`, `processed` / `sent` flags, jobs polling `status = 'pending'`: outbox or inbox candidates
- **unguarded decisions** — a dirty read (`NOLOCK`, `READ UNCOMMITTED`) or a read-then-update in separate statements deciding a write: contested-quantity candidates
- **authorization** — role, profile, or user checks gating a write (who may approve, cancel, exceed a value), and checks that only hide a button with no server-side guard: invariant or state-machine candidates
- **write guards** — validations run before a write (required fields, ranges, formats, allowed transitions) that no constraint repeats: invariant candidates

Code is an oracle of behavior, not of correctness: every finding is a candidate relation, invariant, or derivation, marked as a gap until the user confirms it. Feed candidate relations through `extract_<dialect>.py census --candidates …` so each reaches the grill sized — "violated by N rows": the census tests candidate edges of **any provenance** (code-excavated, agent-hypothesized where cryptic names defeat name-implication). Size the other candidates the same way wherever a count exists — rows with negative stock, rows stuck in a queue.

Sweep application code only: `db-schema/` and `docs/db-model/` are this adoption's own output, so a match there is circular. Honor each application's `.gitignore` (ignored trees are derived or vendored state), skip non-code and oversized files (dumps, assets, binaries), and pass these exclusions to every delegated batch.

The applications are not the whole blast radius. Put to the user the two questions no excavation can answer: **who else reads or writes this database** — other systems, BI/ETL, replication, scheduled jobs, direct access — each with its direction; and **where else a business rule is computed** — spreadsheets, other systems, manual procedures. A spreadsheet named here is the natural oracle for its rule. Record both answers with the gaps; an unknown answer is itself a recorded finding.

Done when both anchors hold — every adopted table traced or flagged untouched, every derived or money-like column traced or flagged writer unknown, each flag re-confirmed under the delegation rule — and both questions have recorded answers.

## 7. Hand off the gaps

Extraction gives structure; it cannot give intent. Close by offering the `database-modeling` grill over the recorded gaps — the live schema and the excavated applications are fact sources it reads, and the candidates enter its themes: type smells into Dialect & portability, consumers and their directions into Boundary, queues and unguarded decisions into Consistency & propagation, protected candidates and rule parameters into its protected-rule marking. When the project has no glossary yet, the grill brings it into existence: each resolved gap lands a term in the glossary or a rule in the model. Report any **harvest candidate** from step 4 in the same hand-off, for the maintainer.
