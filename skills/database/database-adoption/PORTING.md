# Reconcile-driven porting

The disclosed branch of step 4 in [`SKILL.md`](SKILL.md), reached when no reference in `scripts/` covers the source engine. The skill ships one extractor on purpose; every other engine is a port this adoption builds. The **PORTING CONTRACT** in the reference's docstring is the source of truth for *what* a port honours — CLI, outputs, finding classes, fingerprint semantics, safety rules — and what it rewrites (connection, catalog reads, DDL rendering, census queries). This file is *how* to build one.

A port is a subproject of its own, built by **reconcile-driven porting**, the way test-driven code is built: the live database is the test, and `reconcile` is red or green. Write a slice, run it, read what the engine answers, fix, run again. A port that has only been written is a draft; a port that has reconciled the live database is a tool. Build it as `db-schema/tools/extract_<source-dialect>.py`, starting its changelog at `1.0.0`. The skill's `scripts/` is the germline and stays read-only throughout; the port is the soma, and it grows in the repo.

## The sequence

Each step is done only when its check holds against the user's real database, under the read-only standing rule.

1. **Connection and probe first.** Port `connect()` and `probe` before any other subcommand: until the probe runs, the read-only guarantee is unproven, and nothing else touches the database. Write the engine's read-safe privilege list explicitly in the code, with the documentation it came from (role attributes and grants, session privileges, `SHOW GRANTS` — whatever the engine exposes), and keep the probe fail-closed: a privilege outside the list pauses the run for the user's acceptance. The driver is a declared dependency: the port names it with its exact install command and fails loudly when it is missing, as the reference does; install it the project's way (its virtual environment when it has one), and ask before installing into a shared interpreter. An engine without accounts (an embedded file such as SQLite) has no privileges to classify: read-only is the open mode — a read-only URI and `PRAGMA query_only = ON` — and the probe verifies both. Every grant reaches the classification, implicit ones included: a privilege the engine hands to every account by default (execute on routines that run with their owner's rights) makes a read-only login write-capable. An accepted re-run records the reason it was given, never one read back from the paused run's `probe.json`, which that run overwrote. Done when the probe classifies the user's real account, or proves the read-only open, and writes `probe.json`.
2. **The object-class census.** From the engine's own documentation, list every object class it supports — the contract's examples are a start, never the list (packages and bodies, materialized views, sequences, synonyms, user-defined types, extensions, rules, partitions, database links, …). A class is more than a named object: sweep the **behavior-bearing attributes** too — properties attached to an object that change what it does or who reaches it, which a walk of object names never meets:
   - access — row-level security policies and the table flag that enables or forces them; grants on tables, routines, and schemas; object ownership; the role memberships the application's account relies on
   - execution — a routine's security mode (definer or invoker), volatility, language, and per-routine settings; a trigger's enabled state; event triggers
   - integrity — a constraint's validation state (created unvalidated, untrusted) and its deferrability
   - storage and platform — deliberate storage settings (fill factor and kin), installed extensions with their version

   Each lands in its object's fingerprint, so a change reconciles as `DRIFT` — a routine switched to another volatility class, or a policy dropped, changes behavior while the shape stays put — or in a carved file of its own kind, or is reported `BLOCKED`. An application built on an ORM keeps this layer in hand-written migrations its ORM schema never sees, which leaves the live database as its only complete record. Done when every class and every behavior-bearing attribute is either read by `inventory` or reported `BLOCKED` with its reason — anything missing from both is the silent omission the contract forbids.
3. **The reconcile loop.** Port `inventory`, `carve`, and `reconcile`, then iterate: carve → reconcile → read the failure → fix the catalog read or the renderer → carve again. Fingerprints hash the normalized catalog shape, so a renderer fix never fakes drift; a `STALE` finding after a renderer change means re-carve, a `DRIFT` means the catalog read is unstable — fix the read. An engine that overloads routines by signature keeps one file per name holding every overload, ordered by signature, so the qualified-name file rule still holds. Done when reconcile against the live database reports no failure outside recorded exceptions and `python db-schema/tools/verify.py` is green — this is the proof the port works.
4. **Census and discover.** Port their queries, aggregates only, catalog identifiers engine-quoted before interpolation. Two traps change what the numbers mean:
   - **Scoped counts.** Row-level security filters what the account sees. The probe records whether the account bypasses it; a count on a table under a policy the account does not bypass is reported as *scoped*, never as the table's size — a zero there is the policy, not an empty table, and would hand `discover` a false elimination candidate. When most tables come back scoped, the census sizes nothing: ask the user for a read-only login that bypasses row-level security (the bypass attribute with no write grant), and re-run it.
   - **Implied edges.** Name-implied foreign keys try the application's naming convention first (an ORM's mapping names the target outright), then the exact-name rule. An exact-name match on a one-to-one extension table, keyed by the same id as the table it extends, is not the target: the edge goes to the table it extends.
   - **Unrecorded dependencies.** Where the engine records no dependencies inside procedural bodies (PostgreSQL tracks them only for SQL-standard `BEGIN ATOMIC` bodies), derive `depends_on` from each body's text against the catalog's names, and state the method in the port's docstring — left empty, every table that only routines touch ranks as unreferenced.

   Done when both run to completion on the live database and write their JSON in the contract's shape.
5. **The kit.** The tools beside the port (`verify.py`, `buildsql.py`, the linter config) read the canonical dialect from `db-schema/.sqlfluff`; when one of them fails on the new dialect, adjust it in the project and note why. A tool can also skip what it does not know without failing: every kind the port carves (roles, extensions, access, …) appears in `buildsql.py`'s output, and every table parses in `erdgen.py`. A kind missing from the build is the silent omission again. Done when `verify.py` runs every stage it has for this dialect.

## Closing the port

Record in the ledger what the port covers and what it reports `BLOCKED`, and report the port as a **harvest candidate** in the hand-off: version, changelog, the engine and version it was proven against. A maintainer decides, outside the run, whether it joins the skill's references: the soma's mutation, selected into the germline.
